建議先開啟本機 Streamlit，並準備以下頁面或畫面：

1. 「資料訊號總覽」：來源、品質、新鮮度與限制。

## 第 1 頁：專案定位

### 頁面要傳達的事

這不是單純把圖表放進 Streamlit，而是一個從官方資料擷取、品質檢查、快照保存、分析驗證到報告交付的資料產品。

### 講稿

「這個專案是我做的 CPBL 中職資料分析平台。它的重點不是單一排名或一張漂亮的圖，而是把公開資料真正做成一個可以重跑、可以追溯、可以被檢查的資料產品。

我把問題拆成幾個階段：先從 CPBL 官方公開頁面取得資料，接著做 schema、主鍵、數值範圍與資料涵蓋量檢查；品質通過後才建立處理後快照，再把資料交給球員評估、版本比較與球探報告。使用者最後拿到的不只是畫面上的結果，也包含結果所依據的資料版本、條件與方法。」

### 轉場

「所以接下來我會先說明，這個產品實際解決誰的問題，以及為什麼我把資料可信度放在排名之前。」

## 第 2 頁：問題與使用情境

### 頁面要傳達的事

CPBL 公開資料分散、格式可能變動、同一球員可能出現在多張表；使用者需要的是能快速查找，又能知道結果是否可信的工具。

### 講稿

「原始問題其實很實際。官方資料分散在不同頁面，同一球員可能同時出現在現役名單、打擊成績與投手成績；如果直接在前端拼資料，容易發生同名誤選、`player_id` 前導零消失、資料更新後無法說明差異，甚至把不完整的資料當成最新排名。

因此我把主要使用情境設計成三個：第一，先快速確認目前資料是否健康；第二，依打者或投手建立有門檻的候選範圍；第三，把候選結果交付成可以分享、下載與重新驗證的報告。這樣產品服務的不只是看數字，也服務後續的判斷與溝通。」

### 面試官可能追問

**問：為什麼不直接做一個排行榜？**

「排行榜可以是入口，但不能是完整產品。沒有資料版本、資格門檻與品質狀態，使用者很難判斷排名是球員真的變化，還是來源頁面漏資料。我把排行榜放在可追溯的資料流程後面。」

## 第 3 頁：官方資料管線與資料來源

### 頁面要傳達的事

所有正式資料都來自 CPBL 官方公開頁面，並且在進入分析前經過標準化與驗證。

### 講稿

「資料來源只限定在 CPBL 官方網域。專案裡的 `mode=api` 是流程相容的參數名稱，不代表我使用私有金鑰或未公開服務；實際資料仍是從官方公開頁面擷取。

擷取時會檢查來源主機、HTTP 回應、頁面分頁完整性與必要欄位。接著把球員身份、球隊、位置、打擊與投球資料分開處理，再用字串型別保存 `player_id`。這個細節很重要，因為 ID 如果被當成整數，前導零可能遺失，跨表合併就會出問題。

目前這一版驗證結果是 459 位官方現役名單球員，打者與投手成績聯集有 461 位球員，這些數字都是本機實際刷新後的資料，不是散落在畫面裡的 Sample Data。」

### 展示動作

切到「資料訊號總覽」，指出來源網域、資料模式、最後驗證時間與品質狀態。

### 轉場

「有來源還不夠，真正的工程問題是：如果來源格式改了，系統怎麼避免錯誤資料繼續往下游流動？」

## 第 4 頁：資料品質閘門與血緣

### 頁面要傳達的事

品質檢查是發布前的阻擋條件，不是事後才看的報表；通過後才建立可追溯快照。

### 講稿

「我把品質檢查做成資料管線的閘門。它會檢查欄位 schema、必要欄位、業務主鍵是否重複、數值是否落在合理範圍、分頁是否完整，以及最低涵蓋量是否達標。品質通過後，Release Health 還會比較相鄰快照，檢查 schema 是否漂移、資料列數是否突然下降，以及快照、歷史與分析報告是否指向同一版本。

如果品質狀態是 `failed`，流程不會建立新的正式快照，也不會繼續產生排名或報告。這個設計是為了讓錯誤在資料層被擋下來，而不是等使用者在前端看到一個看似合理的數字。

每次通過驗證的處理後資料都會留下快照，包含時間、來源、前一版本與 SHA-256 內容指紋。現在已累積 11 份已驗證快照，最新快照 ID 是 `20260820T145729Z-02041d39eeea`。所以我可以回答『這個結果是哪一版資料算的』，也可以回答『相鄰版本到底改了什麼』。」

「快照解決本機資料血緣，公開發布 Manifest 則解決 GitHub 交付完整性。它只接受固定的 11 個公開 CSV／JSON，記錄每個檔案的 SHA-256、大小、CSV 列數與欄位，再以 canonical JSON 產生 `release_id`。目前 `release_id` 是 `rel-00fdf3a7edc5c76244f240bd`。審查者可執行 `python -m src.verify_public_release reports/metrics/public_release_manifest.json`；只要其中一個檔案被替換、漏掉或混入非 allowlist 路徑，驗證與 release gate 都會失敗。這是完整性校驗而不是數位簽章，發布者身分仍由 Git 與 Pull Request 審查鏈確認。」

### 面試官可能追問

**問：如果 CPBL 官網欄位改名怎麼辦？**

「先由 schema 驗證讓刷新失敗，避免靜默產生錯誤結果；接著查看失敗報告與原始來源差異，再更新 parser、測試與資料品質規則。這比讓錯誤資料先進入排行榜更容易定位，也更容易在 CI 裡阻擋。」

## 第 5 頁：產品介面與核心操作流程

### 頁面要傳達的事

介面是為了完成分析任務，不是只展示視覺效果；每個控制項都會影響實際資料查詢或分析結果。

### 講稿

「前端流程從資料訊號總覽開始，使用者先看到資料來源、品質、新鮮度與限制。接著進入球探工作台，可以切換打者或投手、調整 `PA` 或 `IP` 資格門檻、選擇評估重點、依球隊與位置篩選，最後選最多四位球員比較。

這些控制項不是假按鈕。它們會真正改變候選母體、資格判斷與畫面上的比較結果。百分位會先在符合球員類型與資格門檻的聯盟母體計算，再套用球隊或位置篩選，避免使用者把一個小範圍結果誤讀成聯盟基準。

在球員個人頁，我把官方身份、當季累積成績、進階指標、聯盟平均、百分位、能力雷達、相似球員與前一份快照的變化集中在一起。若樣本不足，頁面會明確標示，而不是硬算一個看起來很精準的分數。」

### 展示動作

1. 切換「打者」與「投手」。
2. 改變 `PA`／`IP` 門檻。
3. 選擇球隊並比較兩位球員。
4. 點入球員個人頁，指出資格狀態、百分位與資料註記。

### 轉場

「當使用者完成一次篩選後，下一個問題是：這個結果能不能離開畫面，成為一份可交付、可重建的分析成果？」

## 第 6 頁：評估方法與分析限制

### 頁面要傳達的事

評估分數是透明的規則型分析，不是神秘黑盒，也不宣稱是未來表現預測。

### 講稿

「這裡的評估方法刻意保持可解釋。打者會分成擊球接觸、選球紀律、長打與整體價值等訊號；投手則分成失分防止、投手價值、控球與三振等訊號。每個評估重點都有固定權重、資格門檻與資料註記。

例如打者的接觸與紀律會用 `0.55` 和 `0.45` 組合；長打與打者價值會用 `0.70` 和 `0.30` 組合。投手的失分防止與投手價值是 `0.75` 和 `0.25`，控球與三振是 `0.70` 和 `0.30`。這些規則都在程式碼、Model Card 與報告裡有明確說明。

我也特別把限制寫清楚：這不是逐球或逐場資料，不是因果推論，也不是未來表現預測，更不會產生投注、比賽結果或名單決策建議。它適合做公開資料的探索、比較與追溯，不應被解讀成超出資料能力的結論。」

### 面試官可能追問

**問：為什麼不用 Machine Learning？**

「目前最重要的問題是資料品質與可追溯性，而不是先堆模型。若輸入資料的定義、涵蓋與版本都不穩定，模型只會把不確定性藏起來。先建立可驗證的資料產品，後續才有條件加入模型，而且可以把模型輸入與評估結果納入同一套血緣與品質流程。」

## 第 7 頁：版本趨勢與分析驗證

### 頁面要傳達的事

產品不只呈現最新結果，也檢查結果是否受資料版本、分布或權重假設影響。

### 講稿

「如果只看最新排名，使用者不知道變化是球員變了，還是資料來源變了。因此我做了兩層驗證。

第一層是版本趨勢：比較時間順序有效的官方快照，列出新增、移除、變更與未變更球員，並保留歷史資料。第二層是分析驗證：對相鄰快照計算 Top-K 重疊率、共同球員數、Spearman ρ、平均排名變化，以及有效涵蓋量、中位數、平均數與四分位數。

另外，我會對評估權重做正負 5%、10% 或 15% 的擾動，再觀察候選排序是否改變。這讓使用者知道排名對資料版本與分析假設的敏感程度。這些都是描述性壓力測試，不會包裝成模型準確率。」

### 展示動作

切到「版本趨勢」與「分析驗證」，指出穩定性、分布變化與敏感度三個區塊。

### 轉場

「驗證完結果後，我希望使用者能把成果帶走，而且在離開網頁後仍然知道它是怎麼產生的。」

## 第 8 頁：球探報告與可重建交付

### 頁面要傳達的事

報告不是畫面截圖，而是帶有資料血緣、條件、方法與完整性指紋的交付物。

### 講稿

「在球探報告頁，使用者可以從符合條件的官方候選人建立最多四人的觀察名單，下載 Markdown 與 CSV。報告會保留球員 ID、球隊、位置或角色、資格量、評估分數、百分位、優勢、風險與資料註記。

更重要的是，系統會同時提供稽核 Manifest。Manifest 記錄 `report_id`、`snapshot_id`、品質狀態、查詢條件、選取球員、分析方法與限制。`report_id` 不依賴產生時間，而是由報告內容與方法形成穩定指紋，所以同一份資料與同一組條件重建時，可以驗證是否一致。

使用者也可以執行 `python -m src.verify_report_manifest` 驗證下載檔案。檔案內容被修改時，驗證會以非零退出碼失敗。這是我希望面試官看到的地方：分析不是只在 UI 裡成立，而是可以被獨立重建與檢查。」

### 展示動作

1. 建立 2～4 位球員的觀察名單。
2. 下載 Markdown、CSV 與 Manifest。
3. 打開 Manifest，指出報告 ID、快照 ID、條件與方法。
4. 說明本機驗證命令。

## 第 9 頁：測試、CI 與安全

### 頁面要傳達的事

專案以可交付標準驗收，而不是以「本機能開」作為完成條件。

### 講稿

「在測試上，我把資料層、分析層、報告完整性、前端主要流程與 release contract 分開驗證。現在又加入 Release Health 與公開發布 Manifest 的異常情境測試，確認列數驟降、schema 漂移、血緣不一致、路徑穿越、symlink、額外檔案與雜湊竄改都會被阻擋。最新本機檢查共有 183 個測試通過，`run_project.bat --check` 也通過 release gate、公開發布驗證、smoke test、依賴檢查與編譯檢查。

CI 分成幾個責任：安全工作流會執行 secrets、依賴與 Bandit 等掃描；品質工作流會用鎖定依賴跑測試、`pip check`、編譯、release gate 與公開發布 Manifest 驗證；資料刷新工作流只把處理後資料與報告產生 reviewable PR，不直接推送 `main`。

在安全上，公開儲存庫不包含 `.env`、Streamlit secrets、API 金鑰、原始 HTML、本機絕對路徑或虛擬環境。資料擷取也限制官方來源主機，使用者輸入會經過驗證。這些設計讓資料更新、程式變更與公開發布都有可檢查的邊界。」

### 面試官可能追問

**問：為什麼資料刷新要開 PR，而不是排程直接改主分支？**

「因為資料刷新本身也是變更。透過 PR 可以保留差異、品質報告與 reviewer 紀錄；如果 schema 或涵蓋量異常，可以在合併前阻擋。這比自動把新資料直接覆蓋正式版本更適合可稽核的資料產品。」

## 第 10 頁：成果、限制與下一步

### 頁面要傳達的事

能清楚說出已完成的價值，也能誠實說出目前沒有做什麼，以及下一步如何擴充。

### 講稿

「目前這個版本已經完成一條完整鏈路：CPBL 官方資料擷取、品質閘門、處理後快照、球員搜尋與個人頁、球探工作台、版本趨勢、分析驗證、可分享報告、單份報告與整組公開資料的雙層 Manifest 驗證、測試、CI 與安全檢查。

我刻意沒有把它說成預測系統，因為目前資料主要是公開累積統計，還不足以支持逐場預測或因果結論。下一步若要擴充，我會優先加入更多可驗證的時間序列與逐場事件資料，先建立資料契約與回溯測試，再評估是否適合加入預測模型；模型也必須沿用同一套 snapshot、quality gate 與 model card。

如果把這個專案交給真實使用者，我希望他不只是看到一個排名，而是知道這個排名來自哪一版資料、用什麼條件算出來、變動是否穩定，以及哪些問題目前資料還回答不了。這就是我認為這個 side project 的價值：把分析結果與工程可信度放在同一個產品裡。」

## 五分鐘精簡版

時間不足時，保留第 1、3、4、5、8、9、10 頁，每頁約 35～45 秒：

1. **定位**：這是可重跑、可追溯、可驗證的資料產品，不是單純圖表 Demo。
2. **資料來源**：只使用 CPBL 官方公開頁面，`player_id` 以字串保存，最新驗證為 459 位現役名單、461 位成績聯集球員。
3. **品質與血緣**：schema、主鍵、數值、分頁與涵蓋量通過才建立快照；目前有 11 份快照與 SHA-256 指紋。
4. **使用流程**：使用者可切換打者／投手、調整 PA／IP、篩選、比較並進入完整球員個人頁；樣本不足會明確提示。
5. **交付**：球探報告提供 Markdown、CSV 與 Manifest，`report_id` 驗證單份分析；公開發布 Manifest 以 `release_id` 驗證 11 個 GitHub 資料產物。
6. **品質與安全**：183 個測試通過，CI 包含 release gate、Release Health、公開發布 Manifest、依賴、Bandit 與 secrets 檢查；資料刷新透過 PR，不直接改 `main`。
7. **價值與限制**：能追蹤資料與分析變化，但不宣稱預測或投注能力；下一步是加入更多可驗證的時間序列或逐場資料。

## 建議現場 Demo 順序

### 兩分鐘快速版

1. **0:00～0:20**：資料訊號總覽，指出來源、品質與時間。
2. **0:20～0:55**：球探工作台，切換打者／投手、調整 PA／IP、選球隊與比較球員。
3. **0:55～1:20**：球員個人頁，指出官方身份、成績、百分位、限制與快照變化。
4. **1:20～1:45**：球探報告，下載 CSV、Markdown、Manifest。
5. **1:45～2:00**：分析驗證，說明 Top-K、Spearman、分布與權重敏感度。

### Demo 時的操作原則

- 先說「我要驗證什麼」，再點控制項，避免變成漫無目的地翻頁。
- 每個結果都指出資料來源、資格門檻或版本條件。
- 若畫面出現樣本不足或空資料，直接把它當成品質設計展示，不要繞過限制。
- 不要現場臨時刷新官方資料，除非面試官要求；先使用已驗證快照確保展示穩定。
- 不要把評估分數說成戰績預測、球隊簽約建議或球員絕對能力。

## 常見問題與回答

### 「這些資料是不是 Sample Data？」

「不是。正式處理資料來自 CPBL 官方公開頁面，流程會限制來源主機並保留資料品質報告、處理時間與快照指紋。畫面上的候選球員不是我手動挑的固定幾個人，而是從完整已驗證資料依條件產生。」

### 「如何證明是最新資料？」

「每次刷新都會留下來源、時間、品質狀態與快照 ID。最新驗證摘要會與 `reports/metrics/data_quality_report.json` 對照；目前 README 的數字就是最近一次 `run_project.bat --check` 的結果，不是手動填一個日期。」

### 「如果資料缺欄位，畫面會怎麼辦？」

「品質閘門會先失敗，正式快照與下游分析不會建立。前端會顯示資料不可用或限制，而不是拿上一段不明來源的數字繼續算。」

### 「為什麼不直接用爬蟲抓完就顯示？」

「因為抓取成功不等於資料正確。產品需要處理來源變動、重複主鍵、分頁遺漏、欄位型別與版本差異；我把這些風險放在資料層處理，再讓前端只消費通過驗證的資料。」

### 「這個分數可以拿來下注或選秀嗎？」

「不應該這樣解讀。它是基於公開累積統計的可解釋比較工具，不是賽果預測，也不提供投注、名單或合約決策建議。介面與文件都會明確標示限制。」

### 「你下一步會怎麼做？」

「先補齊更多時間序列與逐場事件資料，建立資料契約、回溯測試與更細的資料品質監控；等輸入穩定後，再評估預測模型是否真的能解決使用者問題，而不是先為了使用 ML 而使用 ML。」
